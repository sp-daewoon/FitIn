FitIn · 코드베이스 안내

FitIn 코드 지도

백엔드를 해온 사람이 이 저장소를 처음 열었을 때 가장 먼저 찾는 것들, 즉 DB는 어디 있고 요청은 어디로 흐르며 코드가 어떤 순서로 실행되는지를 설명합니다.

2026-09-13 기준 · React Native + Expo + TypeScript · 서버 없음

결론부터 백엔드 개념 대응표 저장소의 실제 모습 코드가 실행되는 순서 화면이 저절로 바뀌는 이유 파일별 역할 다국어 처리 서버는 언제 붙나 테스트 구조 백엔드 출신이 헷갈리는 것

결론부터

가장 궁금해하시는 질문 두 개에 먼저 답합니다.

DB 연결이 어디 있나요

없습니다. 연결 문자열도, 커넥션 풀도, 마이그레이션 러너도 없습니다. FitIn은 지금 서버를 한 번도 호출하지 않습니다. 사용자의 모든 데이터는 폰 안의 키-값 저장소 한 칸에 들어갑니다.

그 한 칸의 이름은 fitin.v4이고, 값은 JSON 문자열 하나입니다. 운동 기록도, 저장한 루틴도, 진행 중인 세션도 전부 그 문자열 안에 있습니다. 테이블이 여러 개인 게 아니라 문서가 하나입니다. MongoDB의 컬렉션에 문서가 딱 하나 있고 그 문서를 통째로 읽고 통째로 쓴다고 보시면 가장 가깝습니다.

읽고 쓰는 코드는 src/storage.ts 29줄이 전부입니다. 그 아래는 @react-native-async-storage/async-storage가 iOS에서는 파일로, 웹에서는 localStorage로 알아서 저장합니다.

로그인은 되어 있나요

아직 아님

로그인 화면도, 인증 코드도, Supabase 클라이언트도 없습니다. package.json에 supabase 의존성이 없고, 앱에 계정 화면이 없습니다. 지금 있는 것은 설계 문서 docs/architecture/SUPABASE.md와 아직 적용하지 않은 SQL supabase/migrations/202609130001_private_routines.sql 두 개뿐입니다. 아래 서버는 언제 붙나에서 자세히 다룹니다.

반면 다국어는 실제로 동작합니다. 영어가 기본이고 한국어를 설정에서 고릅니다. 다국어 처리를 보세요.

백엔드 개념 대응표

Spring이나 Express에서 하던 계층이 여기서는 어느 파일에 해당하는지 먼저 보시면 나머지가 훨씬 빨리 읽힙니다.

백엔드에서 부르던 이름FitIn에서의 자리비고
도메인 / 서비스 계층 src/workout.ts 순수 함수만 있습니다. 계산과 규칙 전부
컨트롤러 / 유스케이스 조립 src/useWorkout.ts 상태를 들고 부수효과를 실행합니다
리포지토리 / DAO src/storage.ts 읽기 한 개, 쓰기 한 개
직렬화 + 스키마 검증 src/codec.ts Jackson과 Bean Validation을 합친 자리
데이터베이스 AsyncStorage 키 fitin.v4 키-값 한 칸. 스키마는 코드가 강제합니다
엔티티 / DTO Data, Session, PlanItem 전부 workout.ts의 타입
DB 마이그레이션 codec.ts의 upgrade() 읽을 때 메모리에서 올립니다. 원본은 안 건드립니다
뷰 / 템플릿 App.tsx와 src/*.tsx 화면을 그리고 사용자 입력을 받습니다
요청 → 응답 주기 상태 변경 → 다시 그리기 주소도 라우터도 없습니다
세션 / 캐시 서버 React 메모리 + 같은 JSON 문서 앱이 죽으면 메모리는 사라지고 문서만 남습니다

가장 중요한 한 줄은 이겁니다. workout.ts는 React도 저장소도 모릅니다. 화면 라이브러리나 AsyncStorage를 import하지 않고, 번역 함수 하나만 가져다 씁니다. 입력을 받아 새 값을 돌려주는 함수들만 있어서, 서버 코드처럼 그냥 단위 테스트할 수 있습니다. 실제로 테스트의 대부분이 이 파일을 향합니다.

저장소의 실제 모습

폰에 실제로 저장되는 값이 어떻게 생겼는지 보는 게 가장 빠릅니다.

// 키: "fitin.v4"  ·  값: 아래 객체를 JSON.stringify 한 문자열 하나
{
  "version": 4,
  "sound": true,
  "preferences": {
    "level": "beginner",
    "split": "custom",            // 어떤 분할 방식을 쓰는지
    "customCycle": ["upper", "lower"],
    "globalRest": 90,             // 세트 사이 휴식 기본값(초)
    "starters": [],
    "savedPlan": null,            // v2 시절 유물. 지우지 않고 보존
    "templates": {                // 방문별로 저장한 "내 기본 루틴"
      "upper": [
        { "machine": "chestPress", "sets": 3, "work": 60, "rest": 90 },
        { "machine": "latPulldown", "sets": 3, "work": 60, "rest": 90 }
      ]
    }
  },
  "history": [                    // 끝난 운동 기록. 배열이 곧 테이블
    { "id": "1757...", "routine": "upper", "endedAt": 1757000000000,
      "elapsed": 1450, "confirmedSets": 6, "completed": true,
      "reason": "routine", "performed": ["chestPress", "latPulldown"] }
  ],
  "session": null                 // 진행 중인 운동. 없으면 null
}

session이 null이 아니면 운동이 진행 중이라는 뜻이고, 그 안에는 단계 목록(phases), 시작 시각(anchor), 지금까지 흐른 초(elapsed), 사용자가 직접 완료를 누른 단계 목록(confirmed)이 들어갑니다. 앱을 껐다 켜도 이 객체가 그대로 남아 있어서 운동이 이어집니다.

스키마는 누가 강제하나

DB에 제약 조건이 없으니 src/codec.ts의 decode()가 그 일을 합니다. 읽어 들인 JSON의 모든 필드를 직접 검사하고, 하나라도 이상하면 예외를 던집니다. 그리고 예외가 나면 앱은 저장을 멈춥니다. 깨진 데이터를 빈 값으로 덮어쓰지 않으려는 의도입니다.

마이그레이션

버전이 올라가면 옛 키를 지우지 않고 새 키를 씁니다. 지금 키는 fitin.v4이고 fitin.v3, fitin.v2, fitin.v1이 폰에 그대로 남아 있습니다. loadData()는 v4가 없으면 v3, 그다음 v2를 찾아 읽고, upgrade()가 메모리에서만 최신 형태로 올립니다. 옛 키에는 절대 다시 쓰지 않습니다. 롤백해도 원본이 남아 있게 하려는 규칙입니다.

코드가 실행되는 순서

읽는 길과 쓰는 길, 두 가지만 알면 나머지는 다 변주입니다.

앱을 켤 때

  1. index.tsregisterRootComponent(App) 한 줄. 여기가 main()입니다.
  2. App.tsx의 FitIn 컴포넌트가 뜬다화면을 그리는 최상위 함수입니다. 안에서 useWorkout()을 부릅니다.
  3. useWorkout이 loadData()를 호출AsyncStorage에서 문자열을 읽어 decode()에 넘깁니다. 비동기라서 이 사이 화면은 "기록을 불러오고 있어요"를 보여줍니다.
  4. 검증 통과 후 setData이 순간 ready가 true가 되고 화면이 실제 내용으로 다시 그려집니다.
  5. 중단된 세션 정산앱이 강제 종료됐다 켜진 경우라면 reconcileOnLaunch()가 비어 있던 시간을 떼어내고 사용자에게 물어봅니다.

운동 중에 "세트 완료"를 누를 때

  1. 버튼의 onPress가 w.command('next')를 부른다App.tsx는 계산을 하지 않습니다. 무슨 일이 일어나야 하는지만 말합니다.
  2. command()가 명령 객체를 만든다{ id, sessionId, phaseId, revision, source, type, at }. 어느 세션의 어느 단계에서, 몇 번째 상태에서 눌렀는지를 함께 넣습니다.
  3. applyCommand()가 판정한다순수 함수입니다. 세션이 다르거나, 단계가 이미 지났거나, 같은 명령이 두 번 오면 아무 일도 하지 않고 원래 객체를 그대로 돌려줍니다. 낙관적 락의 버전 필드와 같은 역할을 revision이 합니다.
  4. 새 Session 객체가 나온다기존 객체를 고치지 않고 복사본을 만듭니다. 그래서 이전 상태가 그대로 남아 비교가 가능합니다.
  5. setData로 교체여기서 두 가지가 동시에 걸립니다. 화면이 다시 그려지고, 저장 효과가 발동해 JSON을 통째로 씁니다.

이 설계가 중요한 이유가 있습니다. 나중에 애플워치나 이어폰에서 같은 명령이 들어와도 똑같은 applyCommand를 통과해야 합니다. 클라이언트마다 타이머를 따로 두지 않는다는 것이 이 프로젝트의 규칙입니다.

화면이 저절로 바뀌는 이유

React를 처음 보면 여기가 제일 낯섭니다. 딱 세 가지만 알면 됩니다.

컴포넌트는 그냥 함수다

function FitIn() { ... return (...) }는 현재 상태를 받아 화면 설명서를 만들어 돌려주는 함수입니다. JSP나 Thymeleaf 템플릿을 함수로 쓴다고 보시면 됩니다. 다만 매 요청마다가 아니라 상태가 바뀔 때마다 다시 호출됩니다.

상태가 바뀌면 함수가 다시 돈다

const [tab, setTab] = useState('today');
// tab은 지금 값, setTab은 "값을 바꾸고 화면을 다시 그려라"

<Pressable onPress={() => setTab('plan')}>

setTab('plan')을 부르면 React가 FitIn()을 다시 호출하고, 바뀐 부분만 실제 화면에 반영합니다. DOM을 직접 건드리거나 새로고침을 하지 않습니다. 캐시를 무효화하면 뷰가 알아서 재생성되는 구조에 가깝습니다.

useEffect는 "이 값이 바뀌면 이걸 해라"

useEffect(() => {
  if (!ready) return;
  void save(data);          // 저장 실행
}, [data, ready]);          // data가 바뀔 때마다

DB 트랜잭션 커밋 후 훅이 돌아가는 것과 비슷합니다. FitIn에서는 이걸로 저장, 음성 안내, 알림 예약, 화면 갱신 타이머를 겁니다. useWorkout.ts에 모여 있습니다.

실제로 있었던 성능 문제

화면 시계를 위해 0.1초마다 상태를 바꾸는 타이머가 운동 중이 아닐 때도 돌고 있었습니다. 그때마다 화면 전체 함수가 다시 실행되니 초당 열 번씩 전부 다시 그려졌고, 버튼이 굼떠졌습니다. 지금은 운동이 실제로 진행 중일 때만 타이머가 돕니다. 상태를 자주 바꾸면 비용이 그대로 든다는 점을 기억하세요.

파일별 역할

줄 수가 큰 순서가 아니라, 읽어야 하는 순서로 정리했습니다.

src/workout.ts
여기가 핵심입니다. 운동 종목 목록, 루틴 구성, 시간 계산, 단계 생성, 명령 판정, 기록 정리가 전부 순수 함수로 들어 있습니다. React도 저장소도 import하지 않습니다. 규칙을 바꾸려면 여기부터 보세요.
src/useWorkout.ts
화면과 엔진 사이를 잇는 조립 담당입니다. 상태를 들고, 저장하고, 음성과 알림을 걸고, 시계를 돌립니다. 컨트롤러에 가장 가깝습니다.
src/codec.ts
저장된 JSON을 믿지 않고 전부 검사합니다. 구버전을 메모리에서 최신 형태로 올리는 일도 여기서 합니다. 스키마 제약과 마이그레이션이 합쳐진 자리입니다.
src/storage.ts
AsyncStorage 읽기와 쓰기. 쓰기는 프로미스 체인으로 줄을 세워 겹치지 않게 합니다.
App.tsx
화면 전체입니다. 상단 탭으로 오늘의 운동, 내 루틴, 운동 사전, 운동 기록을 오갑니다. 가장 길지만 계산은 하지 않습니다. 그리고, 누르면 엔진에 알립니다.
src/RoutinePlanner.tsx
내 루틴 화면. 오늘과 다음 방문 미리보기, 루틴 종류 선택, 맞춤 주기 설정.
src/RoutineBuilder.tsx
계속 유지되는 기본 루틴을 편집하는 화면. 종목 추가와 삭제, 순서, 세트 수, 세트당 시간, 휴식.
src/ExerciseVisual.tsx
운동 그림 한 장. 큰 이미지 한 장에서 필요한 칸만 잘라 보여줍니다.
src/i18n.ts · src/locales/en.json
번역. 한국어 문장이 곧 키이고, 영어 사전이 따로 있습니다.
src/audio.ts · notifications.ts
음성 안내와 화면 밖 알림. 기기에서만 실제로 동작하며 테스트로 검증되지 않습니다.
tests/*.test.ts
Node 기본 테스트 러너로 도는 순수 함수 테스트. 화면 테스트는 없습니다.

다국어 처리

키를 따로 만들지 않는 방식이라 처음 보면 헷갈립니다.

보통 messages.properties에 workout.today=오늘의 운동처럼 키를 만들지만, FitIn은 한국어 문장 자체가 키입니다. 

t('오늘의 운동')

// 한국어일 때  → 키를 그대로 반환 → "오늘의 운동"
// 영어일 때    → en.json에서 찾음  → "Today's workout"

사전은 src/locales/en.json 하나이고 지금 항목이 474개입니다. 영어 번역이 없으면 예외를 던집니다. 화면에 한국어가 섞여 나가는 대신 테스트에서 먼저 터지게 하려는 설계이고, tests/i18n.test.ts가 이를 확인합니다.

주의할 점 하나. 저장되는 ID는 절대 번역하지 않습니다. chestPress나 upper 같은 값은 데이터이고, 화면에 보일 때만 이름으로 바뀝니다.

서버는 언제 붙나

지금 있는 것과 없는 것을 명확히 나눕니다.

항목상태위치
설계 문서있음docs/architecture/SUPABASE.md
테이블 SQL작성됨, 미적용supabase/migrations/…_private_routines.sql
RLS 검증 스크립트있음 (Docker 필요)npm run test:rls
Supabase 클라이언트없음의존성 미설치
로그인 화면없음—
동기화 코드없음—

설계된 테이블은 routine_libraries 하나이고, 사용자당 한 행입니다. 지금 폰에 있는 preferences 문서를 jsonb 컬럼에 통째로 넣는 구조라 로컬 저장 방식과 모양이 같습니다. 운동 기록과 진행 중인 세션은 올리지 않습니다. SQL의 체크 제약이 session과 history 키가 들어오면 거부하도록 되어 있습니다.

동시 편집은 revision 컬럼으로 막습니다. 마지막으로 읽은 값을 조건에 넣고 UPDATE 해서 갱신된 행이 0이면 충돌로 처리합니다. 백엔드에서 쓰던 낙관적 락 그대로입니다. 트리거가 revision을 올리고, RLS 정책이 auth.uid()로 소유자만 접근하게 합니다.

읽는 순서

서버 작업을 시작하실 거라면 docs/architecture/SUPABASE.md의 "운영자가 준비할 것" 여섯 항목부터 보세요. Apple과 Google 인증 설정, 이메일 발신 도메인, 계정 삭제 정책처럼 코드보다 먼저 결정해야 하는 것들이 정리되어 있습니다.

테스트 구조

테스트가 왜 한쪽에만 몰려 있는지에 대한 설명입니다.

npm run check      # 타입 검사 + 테스트 + 문서 정합성 검사
npm test           # tsx --test tests/*.test.ts
npm run build:web  # 웹으로 실제 번들이 되는지 확인

테스트는 전부 Node 기본 러너로 돌고, 순수 함수만 검증합니다. 화면 렌더링 테스트는 하나도 없습니다. React 테스트 환경이 설치되어 있지 않기 때문입니다.

그래서 규칙이 하나 생깁니다. 중요한 판단은 workout.ts에 두세요. 화면 파일에 계산을 넣으면 그 순간 테스트로 지킬 수 없는 코드가 됩니다. 시간 계산, 명령 판정, 루틴 구성이 전부 엔진에 있는 이유입니다.

npm run harness:check는 코드가 아니라 문서를 검사합니다. docs/requirements.json에 적힌 요구사항이 실제 파일을 가리키는지, 문서 사이 링크가 깨지지 않았는지 확인합니다. 문서와 코드가 따로 노는 것을 막는 장치입니다.

백엔드 출신이 헷갈리는 것

실제로 이 저장소에서 문제를 일으켰던 것들입니다.

객체를 직접 고치면 화면이 안 바뀝니다

// 안 됨: 값은 바뀌지만 React가 알아채지 못합니다
session.elapsed = 100;

// 맞음: 새 객체를 만들어 교체합니다
setData(d => ({ ...d, session: { ...d.session, elapsed: 100 } }));

React는 객체가 같은 것인지만 비교합니다. 안을 들여다보지 않습니다. 그래서 항상 복사본을 만듭니다. workout.ts의 모든 함수가 새 객체를 돌려주는 이유입니다.

저장은 직접 부르지 않습니다

save()를 코드에서 찾아 부르지 마세요. setData로 상태를 바꾸면 useEffect가 알아서 저장합니다. 두 번 부르면 쓰기가 겹칩니다.

화면 파일에 계산을 넣지 마세요

새 규칙이 필요하면 workout.ts에 함수로 넣고 테스트를 쓴 다음, 화면에서는 그 함수를 부르기만 하세요. 이건 이 저장소의 명시된 규칙이기도 합니다.

시간은 벽시계 기준입니다

운동 경과 시간은 서버 시각이 아니라 폰의 시계로 계산합니다. 화면을 꺼도 시간은 흐르고, 앱이 완전히 죽었다 켜지면 그 공백은 빼고 사용자에게 물어봅니다. 자세한 규칙은 docs/architecture/SESSION.md에 있습니다.

빌드가 두 갈래입니다

웹은 npm run web으로 바로 뜹니다. iOS는 Expo가 네이티브 프로젝트를 만들어낸 뒤 Xcode로 빌드합니다. ios/ 폴더는 생성물이라 저장소에 없습니다. Debug 빌드는 자바스크립트를 앱에 넣지 않고 맥의 개발 서버에서 받아오고, Release 빌드는 통째로 구워 넣어 인터넷 없이 동작합니다. 절차는 docs/architecture/IOS_BUILD.md에 있습니다.
