# 계정·동기화·환경 분리 결정 기록

작성 2026-09-13. 사용자와의 논의에서 확정된 **정책**만 적는다. 테이블 구조, 라이브러리 선택, 화면 구성, 파일 배치는 여기서 정하지 않는다. 구현자가 이 정책을 만족하는 방법을 스스로 설계한다. 기존 로컬 운동 기능은 계속 동작해야 한다.

아래 "확정"은 다시 논의하지 말고 그대로 따른다. "미결정"은 임의로 정하지 말고 사용자에게 묻는다.

## 확정 · 계정과 신원

- **로그인이 기본이다.** 첫 진입 화면은 로그인·가입 화면이다.
- **둘러보기는 유지한다.** 가입하지 않고도 운동할 수 있어야 한다. 로그인을 강제하지 않는다.
- 로그인 이후에는 토큰 기반 세션으로 동작한다.
- 계정 삭제는 앱 안에서 가능해야 한다. Apple 요구사항이다.

### 가입 경로

가입 경로는 세 가지이고 **어느 하나만으로도 단독 가입할 수 있다.** 이메일 가입을 먼저 해야 하는 구조가 아니다.

1. 이메일 직접 가입 · **인증번호 방식으로 확정.** 비밀번호를 쓰지 않는다. 메일로 받은 번호를 입력해 가입과 로그인이 한 번에 끝난다. 비밀번호 재설정, 비밀번호 규칙, 유출 대응이 모두 필요 없다.
2. Google
3. Apple

**인증번호 방식이라 메일이 도착하지 않으면 로그인 자체가 불가능하다.** 비밀번호 우회 경로가 없다. 메일 전달은 선택적 편의가 아니라 로그인의 필수 경로이므로 아래 발송 항목을 반드시 함께 볼 것.

**SNS로 단독 가입한 경우에도 제공자가 준 이메일을 그 계정의 이메일로 사용한다.**

### 한 이메일에 계정 하나

**같은 이메일 주소로 두 개의 계정이 만들어지지 않는다.** 이미 그 이메일로 계정이 있으면 다른 경로로는 가입도 로그인도 되지 않는다.

충돌했을 때 **자동으로 연결하지 않는다. 안내하고 멈춘다.**

- Google로 가입한 이메일로 이메일 로그인을 시도하면, Google로 가입했다고 알려주고 끝낸다.
- 이메일로 가입한 주소로 Google 로그인을 시도하면, 이메일 가입 내역이 있다고 알려주고 끝낸다.

이 안내는 해당 이메일이 가입되어 있다는 사실을 알려주는 것이기도 하다. 사용자 편의를 위해 그렇게 하기로 한 선택이며, 의도된 절충이다.

### SNS 연동은 이메일 가입자 전용 기능

- 연결은 **설정의 SNS 연동 화면에서만** 일어난다. 로그인한 사용자가 직접 누를 때만이다. 로그인 시도나 가입 시도로는 절대 연결되지 않는다.
- **이 기능은 이메일로 가입한 계정에만 제공한다.** 이메일로 가입한 사람이 Google이나 Apple로도 로그인하고 싶을 때 쓰는 편의 기능이다.
- **SNS로 가입한 계정에는 이 기능을 제공하지 않는다.** Google로 가입한 사람이 Apple을 추가하거나 이메일을 추가하는 경로는 없다.
- 연동하려는 SNS가 이미 다른 계정에 묶여 있으면 거부한다.
- 연동 후에는 두 경로 모두로 같은 계정에 로그인된다.

### 결과적으로 계정 병합은 발생하지 않는다

같은 이메일로 두 계정이 만들어질 수 없고, 연동은 로그인한 본인 계정에 로그인 수단을 더하는 것뿐이라 **합쳐야 할 두 벌의 데이터가 생기지 않는다.** 기록을 합치거나 루틴 중 하나를 버리는 규칙은 필요 없다. 이 단순함이 이 모델의 가장 큰 이점이므로, 나중에 어떤 이유로든 자동 연결을 도입하면 이 이점이 사라진다는 점을 기억할 것.

### 구현에서 반드시 지킬 것

- **SNS 로그인 조회는 제공자의 고유 사용자 식별자를 기준으로 한다.** 이메일은 제공자 쪽에서 바뀔 수 있다. 이메일로만 찾으면 그때 로그인이 끊긴다. 이메일은 계정에 저장하는 값이지 SNS 로그인의 조회 키가 아니다.
- **Apple은 이메일과 이름을 최초 승인 때 한 번만 준다.** 그때 보존하지 않으면 다시 받을 수 없다.
- **Apple 이메일 가리기를 쓰면 계정 이메일이 중계 주소가 된다.** 실제 이메일과 다르므로, 그 사용자가 나중에 실제 이메일로 가입하면 충돌이 감지되지 않고 별도 계정이 만들어진다. 이는 이 모델에서 피할 수 없으며 받아들인다.
- **인증 제공자의 기본 동작이 자동 연결이라면 꺼야 한다.** 검증된 이메일이 같으면 같은 사용자로 묶는 동작이 기본값인 경우가 많다. 이 모델은 묶지 않고 안내해야 하므로, 실제 API로 세 가지 경로를 모두 시도해 계정이 따로 유지되는지 확인할 것. SQL 수준 확인만으로는 인증 동작을 검증한 것이 아니다.

### 감수하기로 한 것

- **SNS 단독 가입자는 로그인 수단이 하나뿐이다.** 그 제공자 계정을 잃으면 앱 안에서 복구할 방법이 없다. 고객지원을 통한 수동 확인 절차가 필요하다.
- SNS 단독 가입자는 다른 로그인 방법을 추가할 수 없다. 편의보다 단순함을 택한 결정이다.

## 확정 · 동기화

- **운동 기록도 동기화한다.** 다른 기기에서 로그인하면 기록이 따라와야 한다. 기존 설계 문서는 루틴만 올리기로 되어 있었으나 이 결정으로 대체한다.
- **로컬이 원본이고 서버는 사본이다.** 기기에 먼저 쓰고 이후 올린다.
- **네트워크가 없어도 운동과 로컬 저장이 가능해야 한다.** 헬스장에서 신호가 없는 상황은 흔하다.
- **토큰이 만료됐다는 이유로 운동을 못 하게 만들지 않는다.** 인증 실패는 동기화를 미루는 사유일 뿐 앱 사용을 막는 사유가 아니다.
- 진행 중인 세션과 타이머 상태는 서버로 올리지 않는다.
- 로그인만으로 어느 쪽 데이터도 말없이 덮어쓰지 않는다.

## 확정 · 환경 분리

- **개발 환경과 운영 환경을 분리한다.** 이 작업을 다른 모든 작업보다 먼저 한다. 계정, 동기화, 광고가 전부 환경에 의존하므로 나중에 하면 전부 다시 손대야 한다.
- **환경마다 앱 식별자가 달라야 한다.** 한 기기에 개발용과 운영용이 동시에 설치되고 서로의 데이터를 건드리지 않아야 한다.
- **개발 앱은 개발 백엔드를, 운영 앱은 운영 백엔드를 호출한다.**
- 환경 설정은 빌드 시점에 결정된다. 이미 빌드된 앱의 접속 대상을 나중에 바꿀 수 없다는 전제로 설계한다.
- **DB 변경은 개발 환경에 먼저 적용해 확인한 뒤 운영에 올린다.**
- 앱에는 공개 가능한 키만 넣는다. 비밀 키는 어떤 경우에도 앱에 포함하지 않는다. 보안은 키를 숨겨서가 아니라 서버 권한 규칙이 책임진다.
- 배포 경로를 내부 테스트와 정식 출시로 나눈다. 올리는 절차와 내리는 절차를 문서로 남긴다.

### 앱 식별자

- **운영용 식별자는 `com.fitin.app`으로 확정한다.** iOS와 Android 모두 같은 값을 쓴다.
- 개발용은 여기서 파생한다.
- **스토어에 처음 올리기 전에 Apple과 Google 콘솔에서 이 값이 사용 가능한지 확인할 것.** 전 세계에서 유일해야 하며 한 번 제출하면 영원히 바꿀 수 없다. 이미 선점되어 있으면 사용자에게 다시 물어야 한다.

### 메일 발송

- **개발 환경은 인증 서비스에 내장된 발송을 쓴다.** 시간당 몇 통 수준으로 제한되지만 개발에는 충분하다.
- **운영 환경은 외부 발송 서비스를 반드시 붙인다.** 내장 발송은 운영용이 아니며 전달을 보장하지 않는다. 인증번호 방식에서는 메일이 안 가면 로그인이 막히므로 타협할 수 없는 항목이다.
- **발송 도메인이 필요하다.** 소유한 도메인에서 보내고 인증 레코드를 설정해야 스팸함으로 가지 않는다. 로그인용 메일이 스팸함에 들어가면 사용자는 로그인하지 못한다.
- 만료 시간, 재전송 제한, 오입력 횟수 제한을 정하고 실제 수신까지 확인한다. 발송 성공을 로그인 성공으로 표시하지 않는다.
- 영어와 한국어 템플릿을 모두 준비한다.

- **비밀 키와 DB 비밀번호는 저장소에 넣지 않는다.** 대화나 이슈에도 남기지 않는다. 앱에 들어가도 되는 것은 공개 키뿐이다.

## 확정 · 백엔드가 관리할 것

- **운동 종목 카탈로그와 루틴 구성을 백엔드에서 관리한다.** 지금은 코드에 박혀 있어서 운동 하나를 추가하거나 오타를 고치는 데도 앱을 다시 빌드해 심사를 받아야 한다. 이 비용을 없애는 것이 목적이다.
- **운동 식별자는 절대 바뀌면 안 된다.** 사용자의 로컬 기록이 그 값을 참조한다.
- **오프라인에서 쓸 기본 카탈로그는 앱 안에 계속 남아 있어야 한다.** 순수한 서버 조회로 바꾸면 오프라인 우선이라는 제품의 근간이 깨진다.
- 관리자 화면은 마지막 단계다. 그전에는 데이터를 직접 넣어도 된다. 콘텐츠를 앱 릴리즈 없이 바꿀 수 있게 되는 것이 먼저다.

## 확정 · 수익화

- **AdMob만 사용한다.** AdSense는 애플리케이션 안에 넣는 것이 정책 위반이다. 웹사이트를 운영할 계획이 없으므로 선택지가 아니다.
- **광고 슬롯의 위치와 노출 금지 규칙은 지금 정해둔다.** 화면 구조를 정리하는 지금이 가장 저렴하다.
- **광고 SDK 실제 통합은 앱 식별자 확정과 계정·동기화 작업 이후다.** SDK는 넣는 순간 개인정보 선언과 동의 절차를 끌고 오고, 기본값이 앱 시작 시 자동 초기화다. 꺼두면 그만이 아니다.
- **버튼 바로 옆에 배너를 두지 않는다.** 운동 중 급하게 누르다 발생하는 오클릭은 무효 트래픽으로 분류되고 계정 정지로 이어진다.
- 개발 환경에서는 반드시 테스트 광고 단위를 쓴다. 실제 광고를 개발자가 누르면 계정이 정지된다.

## 확정 · 먼저 필요한 구조 작업

- **App.tsx를 화면 단위로 분해한다.** 현재 1454줄 한 컴포넌트에 화면 다섯 개가 조건 분기로 들어 있고 네비게이션이 없다. 로그인 흐름은 화면이 여러 개이므로 지금 구조 위에 얹으면 급격히 나빠진다. **로그인 화면을 만들기 전에 끝내야 가장 싸다.**
- 데이터가 드나드는 지점이 현재 한 곳으로 모여 있다. 동기화를 붙일 때 이 성질을 깨지 않는다. 화면 코드가 저장소를 직접 호출하게 만들지 않는다.
- 인증 토큰은 일반 로컬 저장소가 아니라 기기의 보안 저장소에 둔다.

## 미결정 · 사용자에게 물어야 할 것

임의로 정하지 말 것.

1. **광고 제거 과금 모델.** 사용자는 월 구독 1달러를 제안했고, 검토 의견은 일회성 구매였다. 광고 제거만으로 구독을 거는 것은 사용자 저항과 심사 근거 양쪽에서 약하고 구현 비용이 몇 배다. 구독을 유지한다면 동기화나 통계 같은 지속적 가치와 묶는 편이 낫다.
2. **운동 진행 중 화면의 광고 노출 여부.** 노출이 가장 많이 쌓이는 화면이 운동 진행 화면이라 수익과 사용 경험이 정면으로 충돌한다. 제품 결정이다.

## 기존 문서와 충돌하는 부분

[Supabase 설계](../architecture/SUPABASE.md)를 이 결정에 맞게 고쳐야 한다. 충돌 지점은 다음과 같다.

- 운동 기록과 세션을 올리지 않는다고 되어 있으나, **기록은 동기화하기로 바뀌었다.** 세션은 그대로 올리지 않는다.
- 계정 루틴이 이미 있으면 두 내용을 비교해 사용자가 고르게 한다고 되어 있으나, **이 모델에서는 그 상황 자체가 생기지 않는다.** 같은 이메일로 두 계정이 만들어지지 않고 연동은 본인 계정에 로그인 수단만 더하므로, 충돌 해소 절차가 필요 없다.
- 계정 연결을 "인증된 세션에서 제공자 소유를 다시 증명하는 별도 흐름"으로 적어둔 부분은 그대로 유효하다. 다만 **이메일 가입자만 쓸 수 있는 기능**이라는 제한이 추가됐다.
- 이메일 가입을 인증번호 방식으로 적어둔 부분은 **확정되어 그대로 유효하다.** 충돌이 아니다.
- 가입 없이 운동하는 경로는 유지되지만 **첫 진입 화면이 로그인·가입 화면으로 바뀌었다.**

## 함께 봐야 할 것

출시를 막고 있는 것은 계정과 광고만이 아니다. [릴리즈 준비 상태](../release-readiness.json)의 항목 일곱 개 중 여섯 개가 미검증 또는 초안이며, 그중 운동 지도 콘텐츠 검수는 부상 위험과 직결된다. 계정 작업과 별개로 진행 상태를 확인할 것.
