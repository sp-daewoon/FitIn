# 계정·동기화·환경 분리 결정 기록

작성 2026-09-13. 사용자와의 논의에서 확정된 **정책**만 적는다. 테이블 구조, 라이브러리 선택, 화면 구성, 파일 배치는 여기서 정하지 않는다. 구현자가 이 정책을 만족하는 방법을 스스로 설계한다. 기존 로컬 운동 기능은 계속 동작해야 한다.

아래 "확정"은 다시 논의하지 말고 그대로 따른다. "미결정"은 임의로 정하지 말고 사용자에게 묻는다.

## 확정 · 계정과 신원

- **로그인이 기본이다.** 첫 진입 화면은 로그인·가입 화면이다.
- **둘러보기는 유지한다.** 가입하지 않고도 운동할 수 있어야 한다. 로그인을 강제하지 않는다.
- 로그인 이후에는 토큰 기반 세션으로 동작한다.
- 계정 삭제는 앱 안에서 가능해야 한다. Apple 요구사항이다.

### 가입 경로

**소셜 로그인만 사용한다. 이메일 가입은 폐지했다.** 이메일을 받으면 인증, 전달, 재전송, 스팸 대응까지 서비스가 계속 커져서 제외하기로 확정했다.

- 지금 넣는 것은 **Google과 Apple** 두 가지다.
- **네이버와 카카오는 나중에 추가한다.** 추가될 때도 아래 규칙은 그대로 적용된다.
- 계정의 이메일은 **제공자가 준 값을 그대로 쓴다.** 사용자가 입력하는 이메일 입력란은 어디에도 없다.

### 한 이메일에 계정 하나

**같은 이메일 주소로 두 개의 계정이 만들어지지 않는다.** 이미 그 이메일로 계정이 있으면 다른 제공자로는 가입도 로그인도 되지 않는다.

충돌했을 때 **자동으로 연결하지 않는다. 어느 제공자로 가입했는지 알려주고 멈춘다.** 예를 들어 Google로 가입한 주소로 Apple 로그인을 시도하면 Google로 로그인하라고 안내한다.

이 안내는 해당 이메일이 가입되어 있다는 사실을 알려주는 것이기도 하다. 사용자 편의를 위해 그렇게 하기로 한 선택이며, 의도된 절충이다.

### 계정 연동 기능은 없다

이메일 가입이 사라지면서 **로그인 방법을 추가하는 기능 자체가 없어졌다.** 연동은 원래 이메일로 가입한 사람이 소셜 버튼을 덧붙이는 편의 기능이었고, 이메일 계정이 존재하지 않으므로 대상이 없다.

- 한 계정에는 **가입할 때 쓴 제공자 하나만** 붙는다.
- Google로 가입한 사람이 Apple을 추가하는 경로는 없다. 반대도 없다.
- 나중에 네이버와 카카오가 들어와도 마찬가지다.

### 결과적으로 계정 병합은 발생하지 않는다

같은 이메일로 두 계정이 만들어질 수 없고 연동 기능도 없으므로 **합쳐야 할 두 벌의 데이터가 생기지 않는다.** 기록을 합치거나 루틴 중 하나를 버리는 규칙은 필요 없다. 이 단순함이 이 모델의 가장 큰 이점이므로, 나중에 어떤 이유로든 자동 연결이나 연동 기능을 도입하면 이 이점이 사라진다는 점을 기억할 것.

### 구현에서 반드시 지킬 것

- **제공자 조회는 제공자의 고유 사용자 식별자를 기준으로 한다.** 이메일은 제공자 쪽에서 바뀔 수 있다. 이메일로만 찾으면 그때 로그인이 끊긴다. 이메일은 계정에 저장하는 값이지 조회 키가 아니다.
- **Apple은 이메일과 이름을 최초 승인 때 한 번만 준다.** 그때 보존하지 않으면 다시 받을 수 없다.
- **Apple 이메일 가리기를 쓰면 계정 이메일이 중계 주소가 된다.** 실제 이메일과 다르므로 그 사용자가 Google로도 가입하면 충돌이 감지되지 않고 별도 계정이 만들어진다. 이는 이 모델에서 피할 수 없으며 받아들인다.
- **규칙은 클라이언트가 아니라 데이터베이스가 강제한다.** 화면을 우회하거나 제공자 설정이 잘못 켜져도 계정이 만들어지면 안 된다.

### 감수하기로 한 것

- **모든 사용자가 로그인 수단을 하나만 갖는다.** 그 제공자 계정을 잃으면 앱 안에서 복구할 방법이 없다. 고객지원을 통한 수동 확인 절차가 필요하며, 지원 창구는 실제로 응답 가능해야 한다.
- 로그인 수단을 추가할 수 없다. 편의보다 단순함을 택한 결정이다.

### 앱 식별자

- **운영용 식별자는 `com.fitin.app`으로 확정한다.** iOS와 Android 모두 같은 값을 쓴다.
- 개발용은 여기서 파생한다.
- **스토어에 처음 올리기 전에 Apple과 Google 콘솔에서 이 값이 사용 가능한지 확인할 것.** 전 세계에서 유일해야 하며 한 번 제출하면 영원히 바꿀 수 없다. 이미 선점되어 있으면 사용자에게 다시 물어야 한다.

### 메일 발송

**인증에 메일이 필요 없어졌다.** 로그인이 소셜 전용이라 인증번호를 보내지 않는다. 별도 발송 서비스와 SMTP 설정은 출시를 막는 항목에서 빠진다.

도메인은 여전히 필요하다. 아래 웹 페이지 때문이며, 발송 때문이 아니다. 나중에 공지나 고객지원 메일을 보낼 일이 생기면 그때 발송 서비스를 붙인다.

### 출시에 필요한 웹 페이지

도메인을 확보하면 메일 발송뿐 아니라 스토어가 요구하는 페이지들도 여기서 해결한다. 정적 페이지 몇 장이면 되고, 별도의 서비스가 아니다.

- **개인정보처리방침.** Apple과 Google 모두 제출 시 URL을 요구한다. 계정과 서버 저장, 삭제 정책을 반영해야 한다.
- **이용약관.** 계정과 결제가 생기므로 필요하다.
- **고객지원 연락처.** Apple이 지원 URL을 요구한다. SNS 단독 가입자가 로그인 수단을 잃었을 때의 수동 확인 창구이기도 하므로 실제로 응답 가능한 주소여야 한다.
- **계정 삭제 안내 페이지.** 앱 안의 삭제 기능과 별개로, Google Play는 앱을 설치하지 않고도 삭제를 요청할 수 있는 웹 경로를 요구한다.

도메인은 메일 인증 레코드를 직접 설정할 수 있도록 DNS 관리 권한을 유지한 채로 둔다. 앱 식별자가 도메인과 일치할 필요는 없다. `com.fitin.app`은 어떤 도메인을 쓰든 그대로 유효하다.

### 준비 상태 · 2026-09-13

- **개발용 Supabase 프로젝트가 연결됐다.** 주소는 `https://janujhxbpuucbwpbpqtl.supabase.co` 이며, 앱은 환경 설정으로 주소와 공개 키를 주입받는다. 가입 사용자는 0명이다.
- **마이그레이션 세 개가 개발 프로젝트에 적용됐다.** 개인 루틴, 계정과 기록, 소셜 전용 인증 순이다. 적용된 마이그레이션은 내용을 고칠 수 없다. 정책이 바뀌면 새 파일을 추가한다.
- **이메일 가입은 데이터베이스에서 거부된다.** 계정 행의 제공자 값이 `google`과 `apple`만 허용하므로, 제공자 설정이 잘못 켜져 있어도 계정이 만들어지지 않는다. 롤백 트랜잭션으로 실제 거부를 확인했다.
- **이 프로젝트는 개발 전용이다.** 운영용 프로젝트는 아직 없으며 별도로 만들어야 한다. 이 프로젝트를 그대로 운영에 쓰면 환경 분리 결정이 무효가 된다.
- **주소와 공개 키를 앱 소스에 직접 쓰지 않는다.** 여기 적어둔 것은 진행 상황 기록이지 코드에 넣으라는 뜻이 아니다.
- **비밀 키와 DB 비밀번호는 저장소에 넣지 않는다.** 앱에 들어가도 되는 것은 공개 키뿐이다.

### 남은 콘솔 작업

코드에서 할 수 있는 일은 끝났다. 아래는 Supabase와 각 제공자 콘솔에서 사람이 해야 하며, 끝나기 전에는 로그인 버튼이 비활성 상태로 표시된다. 앱은 설정되지 않은 제공자를 절대 활성처럼 보여주지 않는다.

1. **Google 제공자 활성화.** Google Cloud에서 OAuth 클라이언트를 만들고 Supabase에 등록한다. 앱으로 돌아오는 주소를 정확히 맞춘다.
2. **Apple 제공자 활성화.** Apple 개발자 등록이 선행된다. iOS는 네이티브 방식을 우선하며, 웹과 Android용으로는 별도 설정이 더 필요하다.
3. **이메일 제공자 비활성화.** 데이터베이스가 이미 막고 있지만, 켜둔 채로 두면 사용자가 원인 모를 오류를 보게 된다.
4. **Access Token Hook 등록.** 준비된 함수를 Supabase의 커스텀 액세스 토큰 훅으로 지정한다. 제공자 설정이 잘못돼도 세션 발급 단계에서 한 번 더 막는다.

설정을 마치면 실제 API로 확인한다. Google로 가입한 뒤 같은 이메일로 Apple 로그인을 시도해 **계정이 합쳐지지 않고 안내가 뜨는지** 직접 볼 것. SQL 수준 확인만으로는 인증 동작을 검증한 것이 아니다.

## 확정 · 백엔드가 관리할 것

- **운동 종목 카탈로그와 루틴 구성을 백엔드에서 관리한다.** 지금은 코드에 박혀 있어서 운동 하나를 추가하거나 오타를 고치는 데도 앱을 다시 빌드해 심사를 받아야 한다. 이 비용을 없애는 것이 목적이다.
- **운동 식별자는 절대 바뀌면 안 된다.** 사용자의 로컬 기록이 그 값을 참조한다.
- **오프라인에서 쓸 기본 카탈로그는 앱 안에 계속 남아 있어야 한다.** 순수한 서버 조회로 바꾸면 오프라인 우선이라는 제품의 근간이 깨진다.
- 관리자 화면은 마지막 단계다. 그전에는 데이터를 직접 넣어도 된다. 콘텐츠를 앱 릴리즈 없이 바꿀 수 있게 되는 것이 먼저다.

## 확정 · 수익화

- **AdMob만 사용한다.** AdSense는 애플리케이션 안에 넣는 것이 정책 위반이다. 웹사이트를 운영할 계획이 없으므로 선택지가 아니다.
- **광고 슬롯의 위치와 노출 금지 규칙은 지금 정해둔다.** 화면 구조를 정리하는 지금이 가장 저렴하다.
- **광고 SDK 실제 통합은 앱 식별자 확정과 계정·동기화 작업 이후다.** SDK는 넣는 순간 개인정보 선언과 동의 절차를 끌고 오고, 기본값이 앱 시작 시 자동 초기화다. 꺼두면 그만이 아니다.
- **버튼 바로 옆에 배너를 두지 않는다.** 운동 중 급하게 누르다 발생하는 오클릭은 무효 트래픽으로 분류되고 계정 정지로 이어진다.
- 개발 환경에서는 반드시 테스트 광고 단위를 쓴다. 실제 광고를 개발자가 누르면 계정이 정지된다.

## 확정 · 먼저 필요한 구조 작업

- **App.tsx를 화면 단위로 분해한다.** 현재 1454줄 한 컴포넌트에 화면 다섯 개가 조건 분기로 들어 있고 네비게이션이 없다. 로그인 흐름은 화면이 여러 개이므로 지금 구조 위에 얹으면 급격히 나빠진다. **로그인 화면을 만들기 전에 끝내야 가장 싸다.**
- 데이터가 드나드는 지점이 현재 한 곳으로 모여 있다. 동기화를 붙일 때 이 성질을 깨지 않는다. 화면 코드가 저장소를 직접 호출하게 만들지 않는다.
- 인증 토큰은 일반 로컬 저장소가 아니라 기기의 보안 저장소에 둔다.

## 미결정 · 사용자에게 물어야 할 것

임의로 정하지 말 것.

1. **광고 제거 과금 모델.** 사용자는 월 구독 1달러를 제안했고, 검토 의견은 일회성 구매였다. 광고 제거만으로 구독을 거는 것은 사용자 저항과 심사 근거 양쪽에서 약하고 구현 비용이 몇 배다. 구독을 유지한다면 동기화나 통계 같은 지속적 가치와 묶는 편이 낫다.
2. **운동 진행 중 화면의 광고 노출 여부.** 노출이 가장 많이 쌓이는 화면이 운동 진행 화면이라 수익과 사용 경험이 정면으로 충돌한다. 제품 결정이다.

## 기존 문서와 충돌하는 부분

[Supabase 설계](../architecture/SUPABASE.md)를 이 결정에 맞게 고쳐야 한다. 충돌 지점은 다음과 같다.

- 운동 기록과 세션을 올리지 않는다고 되어 있으나, **기록은 동기화하기로 바뀌었다.** 세션은 그대로 올리지 않는다.
- 계정 루틴이 이미 있으면 두 내용을 비교해 사용자가 고르게 한다고 되어 있으나, **이 모델에서는 그 상황 자체가 생기지 않는다.** 같은 이메일로 두 계정이 만들어지지 않고 연동은 본인 계정에 로그인 수단만 더하므로, 충돌 해소 절차가 필요 없다.
- 계정 연결 흐름은 **기능 자체가 없어졌다.** 한 계정에는 가입에 쓴 제공자 하나만 붙는다.
- 이메일 가입과 인증번호 방식은 **폐지됐다.** 로그인은 소셜 전용이며, 해당 서술과 이메일 발송 준비 항목은 더 이상 유효하지 않다.
- 가입 없이 운동하는 경로는 유지되지만 **첫 진입 화면이 로그인·가입 화면으로 바뀌었다.**
